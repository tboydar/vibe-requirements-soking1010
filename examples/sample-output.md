# 需求文件範例：寵物散步媒合平台

> 以下是 Vibe Requirements Skill 探索完成後的產出範例，展示最終文件的結構與寫法。

## 1. 產品概述

許多上班族養了寵物卻經常加班，沒時間帶毛孩出門散步。這個平台媒合「需要遛狗服務的飼主」和「願意幫忙遛狗的散步員」，讓飼主透過 App 預約附近的散步員，並在散步過程中即時追蹤寵物狀況。

## 2. 複雜度評估

**Lv3：服務門市（前台與後台）**

這是一個典型的「內外有別」系統——就像一間便利商店，有店員用的後台和客人用的前台：

- **前台（飼主端）**：搜尋散步員、預約服務、追蹤散步進度、評價
- **後台（散步員端）**：管理時段、接受/拒絕預約、回報散步狀態
- **管理後台**：審核散步員資格、處理糾紛、查看營運數據

飼主和散步員是兩群不同的角色，操作邏輯完全不同，但共用同一份資料（預約記錄、寵物資料）。

## 3. 核心 User Stories

### Story 1：飼主預約散步服務

```
作為一名飼主，
我想要搜尋並預約附近的散步員，
以便於在我無法出門時，毛孩也能得到充足的運動。

驗收標準：
1. 飼主可依地區、時段、評價篩選可用的散步員
2. 預約需填寫：日期、時段（30分鐘/60分鐘）、寵物、特殊注意事項
3. 送出預約後，散步員需在 30 分鐘內回覆接受或拒絕
4. 若超時未回覆，系統自動取消並建議其他散步員
```

### Story 2：散步員管理可接單時段

```
作為一名散步員，
我想要設定每週可接單的時段，
以便於只在我方便的時間接到預約請求。

驗收標準：
1. 可以按週設定固定時段（例如：每週一三五 14:00-18:00）
2. 可以臨時關閉或新增某天的特定時段
3. 已有預約的時段不可被關閉（需先與飼主協調取消）
4. 時段設定後立即反映在飼主的搜尋結果中
```

### Story 3：飼主即時追蹤散步進度

```
作為一名飼主，
我想要在散步進行中看到即時的路線與照片，
以便於安心知道毛孩的狀態。

驗收標準：
1. 散步開始後，飼主可在地圖上看到即時路線（每 30 秒更新一次）
2. 散步員可拍照上傳，飼主即時收到通知
3. 散步結束後，系統自動產生散步報告（路線圖、距離、時長、照片）
4. 飼主可對本次服務評分（1-5 星）並留言
```

## 4. 系統架構建議

作為 Lv3 系統，重點放在**前後台的關注點分離**和**統一的資料介面**：

- **關注點分離**：飼主端重體驗與動線引導；散步員端重效率與防呆；管理後台重數據總覽
- **統一介面**：三個端共用同一組 API，但依角色回傳不同的資料範圍
- **封裝**：地圖追蹤、通知推播、付款等功能各自獨立模組，互不影響

## 5. Edge Cases 清單

- 散步途中散步員手機沒電或斷網 → GPS 斷點如何處理？
- 寵物在散步途中受傷或走失 → 緊急通知機制？保險？
- 散步員臨時爽約 → 自動媒合替補？違約處理？
- 飼主在散步中途取消 → 費用如何計算？
- 惡劣天氣 → 是否自動建議改期？
- 同一時段多隻寵物 → 散步員可以同時遛幾隻？

## 6. EARS 格式需求

**隨時作用型：**
- 系統應該要以 HTTPS 加密所有傳輸資料
- 系統應該要在 3 秒內回應使用者的操作

**事件驅動型：**
- 當散步員點擊「開始散步」時，系統應該要啟動 GPS 追蹤並通知飼主
- 當飼主送出預約請求時，系統應該要推送通知給散步員

**異常處理型：**
- 如果 GPS 訊號中斷超過 5 分鐘，那麼系統應該要通知飼主並顯示最後已知位置
- 如果散步員未在預約時間前 15 分鐘確認出發，那麼系統應該要發送提醒通知

**狀態驅動型：**
- 當散步處於進行中狀態時，系統應該要每 30 秒更新散步員的位置到地圖上
- 當預約處於「待確認」狀態超過 30 分鐘時，系統應該要自動取消並通知飼主
