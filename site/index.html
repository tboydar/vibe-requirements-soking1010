Vibe Requirements

需求探索助手

「魔法是想像的世界，無法想像的東西就無法用魔法實現。」

幫助 Vibe Coder 從模糊的產品想法，一步步釐清需求、定義系統複雜度、撰寫 User Story，最終產出可以直接交給 AI 開發的完整需求文件。

五階段工作流程

整個探索分為五個階段，根據你的狀態靈活切換，不必死板按順序走。

階段 1

接住想法

Catch the Vibe

用 CARNET 框架中最關鍵的問題打開對話，快速建立「問題空間」的邊界。一句話複述核心想法，確認方向。

階段 2

判斷複雜度

Gauge Complexity

幫你定位在五個複雜度層級中的哪一層。不同層級的系統設計截然不同，這個判斷會影響後續所有決策。

階段 3

產品分層思考

Think in Layers

用「蓋 Shopping Mall」的比喻，引導你從上到下想清楚五個層面：戰略、範圍、結構、框架、表現。

階段 4

寫出 User Story

Write Stories

把前面的探索結果轉化為標準的 User Story，含驗收標準，並用 MoSCoW 法排定優先級。

階段 5

需求品質檢查

Verify with EARS

用 EARS 語法檢查每條需求是否夠清楚，強迫想清楚「什麼時候觸發」、「誰執行」、「做什麼」。

CARNET 需求訪談框架

CARNET 原意是「通行證」，象徵當我們掌握這六大要素，就能進入需求方的世界，理解背後的真實動機與限制。

C

Constraint 限制

需求方在資源、時程、人力或組織結構上的限制條件。

  • 專案的預算與時間範圍大概是多少？
  • 有哪些規定或條件是不可動搖的？
  • 哪些部門或環節可能會卡住流程？
A

Aspiration 期待

需求方對於成功樣貌的想像與描述。

  • 您最希望這個專案完成後能帶來什麼？
  • 如果要用一個具體成果衡量成功，會是什麼？
  • 對您來說，這個專案的最佳狀態是什麼？
R

Role 身份

眼前人的身份、權限與決策影響力。

  • 您在這個專案中扮演什麼角色？
  • 誰會是最終的決策者？
  • 其他哪些利害關係人會參與？
N

Need 需求來源

專案為什麼此時此刻出現？背後的觸發點。

  • 這個需求是怎麼被提出的？
  • 最近發生了什麼事件讓專案變得急迫？
  • 如果這次專案沒有執行，會有什麼影響？
E

Experience 經驗

過去類似的嘗試與學到的教訓。

  • 過去有沒有做過類似專案？結果如何？
  • 哪些經驗會影響這次規劃？
  • 之前最大的挑戰或阻礙是什麼？
T

Trust / Thoughts 信念

需求方對「應該怎麼做」的信念、偏好與預設立場。

  • 您認為這類專案要怎麼做才會成功？
  • 選擇合作夥伴時，您最看重什麼？
  • 在您心中，什麼樣的失敗是不能接受的？

快速模式（自己做給自己用）

只需要回答三個核心問題，30 秒搞定：

  1. 我想解決什麼問題？（N）
  2. 做完之後理想的樣子是什麼？（A）
  3. 我有多少時間和能力？（C）

標準模式（做給別人用）

完整自問自答六個面向：

  1. 我是為誰做這個？（R）
  2. 為什麼現在要做？（N）
  3. 做完之後最理想的結果是什麼？（A）
  4. 我之前試過什麼？學到什麼？（E）
  5. 時間、預算、技術能力有什麼限制？（C）
  6. 我相信什麼樣的做法是對的？（T）

數位空間複雜度的五個層級

每個數位產品都可以對應到一個複雜度層級。層級越高，需要處理的「人與人之間的關係」就越複雜。判斷正確的層級，能避免過度設計或設計不足。

Lv1

個人工作室

自家書桌

只有你擁有這個系統的使用權，工具的擺放、流程完全隨你高興。

  • 不需要登入系統
  • 資料儲存在本機端
  • 不需要考慮多人同時操作

個人記帳工具、個人筆記 App、本地端計算器

Lv2

私人辦公室

公司辦公室

雖然大家都在同個空間，但有「職位分工」——老闆可以看到財報，員工只能看到自己的打卡記錄。

  • 需要身分驗證（登入）
  • 需要權限分級
  • 資料存在伺服器端，多人共用

HR 人事系統、公司內部專案管理工具、團隊知識庫

Lv3

服務門市

便利商店

空間切分為二：後台是店員操作 POS 機，前台是路人進來結帳。兩套不同的使用介面。

  • 兩套不同的使用介面
  • 同一份資料，不同的操作邏輯
  • 外部用戶可能需要註冊

餐廳點餐系統、電商網站、預約系統

Lv4

大眾運動場

開放運動中心

所有人都可以進去註冊使用、互相交流。感受不到「內部店員」在裡面服務。

  • 大量用戶同時操作
  • 用戶之間有互動
  • 需要處理資源搶奪

社群平台、論壇、線上學習平台

Lv5

數位百貨商場

百貨公司

最複雜的層次——你是百貨老闆，不特定的櫃位老闆進駐，另一群消費者進去各櫃位買東西。

  • 三層角色：平台管理者、租戶、終端用戶
  • 資料完全隔離
  • 每個租戶可以客製化自己的空間

開店平台（Shopify）、企業 SaaS 工具

如何判斷你的產品在哪一層？

  1. 只有我自己用嗎？ → 是 → Lv1
  2. 使用者都是同一個組織內部的人嗎？ → 是 → Lv2
  3. 有「服務提供方」和「服務接受方」的區別嗎？ → 是 → Lv3
  4. 所有用戶都是平等的，可以互相互動嗎？ → 是 → Lv4
  5. 會有「第三方入駐」、每個入駐方有自己的客戶嗎？ → 是 → Lv5

原則：先用最低層級驗證核心假設，再隨需求成長升級。

數位產品的五個思考層級

用「蓋 Shopping Mall」的比喻理解每一層，從最抽象（為什麼做）到最具體（看起來如何）。

1

戰略層 為什麼要蓋？

思考商業目標與用戶期待。

  • 我做這個是為了解決什麼問題？
  • 目標用戶是誰？他們現在怎麼處理這個問題？
  • 成功的衡量標準是什麼？
2

範圍層 裡面該有什麼？

定義功能與內容的範疇。

  • 核心功能有哪些？
  • 哪些是第一版必須做的？哪些可以之後再加？
  • 需要什麼樣的內容？
3

結構層 樓層邏輯與動線

規劃資訊架構與互動流程。

  • 功能之間的關係是什麼？哪些要放在一起？
  • 使用者完成一件事的步驟是什麼？
  • 資料之間的關係是什麼？
4

框架層 細部藍圖

規劃介面佈局和導航。

  • 主要操作按鈕放在哪裡？
  • 使用者怎麼在不同功能間切換？
  • 重要資訊放在畫面的什麼位置？
5

表現層 室內設計與感官

影響用戶感官的表現元素。

  • 整體視覺風格是什麼？
  • 色彩和字體的選擇？
  • 動畫和過場效果需要嗎？

常見錯誤：Vibe Coder 最容易從下往上想——「我想要一個有很漂亮動畫的登入頁面」，但其實還沒想清楚誰會來登入、為什麼要登入。正確的順序是從上往下：先確認戰略層和範圍層，再去想結構層和框架層，最後才是表現層。

User Story 與 MoSCoW 優先級

把探索結果轉化為標準的 User Story，讓需求具體到可以直接開發。

User Story 格式

作為一名 [角色]，
我想要 [功能]，
以便於 [價值]。

驗收標準：
1. [具體可驗證的條件]
2. [具體可驗證的條件]
3. [具體可驗證的條件]

撰寫原則

  • 一個 Story 只描述一件事
  • 驗收標準必須可以「打勾確認」，不能是「系統要好用」
  • 主動思考 Edge Case：資料格式不對？網路斷了？輸入空白？
  • 核心功能用 3-7 個 Story 涵蓋，先聚焦最重要的 3 個

MoSCoW 優先級排序

寫完 User Story 後，用 MoSCoW 法幫每個 Story 標上優先級：

Must

沒有就不能上線

核心價值的最小實現。如果只能上線三個功能，你選哪三個？那三個就是 Must。

Should

很重要但第一版可以簡化

提升體驗但非必要。使用者沒有這個功能仍然能完成核心任務。

Could

有很好，沒有也行

錦上添花的功能。有時間再做，沒有也不影響產品的核心價值。

Won't

這次不做

記下來，留給未來版本。明確說「不做」比模糊的「以後再說」更有用。

EARS 需求語法

Easy Approach to Requirements Syntax — 一套幫助你把需求「寫得讓機器（或 AI）不會誤解」的寫作規則。用五種固定句型，強迫你把每條需求寫清楚。

隨時作用型

Ubiquitous

系統應該要 [動作]

系統永遠都要遵守的規則，沒有特殊觸發條件。

例：系統應該要以 HTTPS 加密所有傳輸資料

事件驅動型

Event-driven

當 [事件] 時，系統應該要 [動作]

只有在特定事情發生時，系統才會動作。

例：當使用者點擊「送出訂單」時，系統應該要顯示訂單確認頁面

異常處理型

Unwanted behaviours

如果 [異常]，那麼系統應該要 [動作]

告訴系統遇到不好的情況時該怎麼辦。

例：如果付款閘道無回應超過 10 秒，那麼系統應該要顯示「付款處理中」並自動重試一次

狀態驅動型

State-driven

當處於 [狀態] 時，系統應該要 [動作]

系統處於某種狀態時，必須持續執行的行為。

例：當使用者處於「編輯模式」時，系統應該要每 30 秒自動儲存草稿

選配功能型

Optional features

如果系統包含 [功能]，系統應該要 [動作]

只有當系統包含特定功能時才適用的需求。

例：如果系統包含多語系功能，系統應該要在首次登入時自動偵測瀏覽器語言

自我檢查清單

  1. 能明確判斷是哪一種句型嗎？
  2. 觸發條件寫清楚了嗎？（什麼時候啟動？）
  3. 執行的動作夠具體嗎？（具體到可以寫程式）
  4. 可以寫測試來驗證這條需求嗎？
  5. 有沒有忘記寫「異常處理型」的需求？（最常被遺漏）

軟體架構與非功能性需求

當需求釐清到一定程度，就需要思考系統的「骨架」。

三層架構

把系統想成一家百貨公司的運作方式：

平台層 — 大門與總服務台

所有人進百貨都從大門進來，在服務台問路。負責把所有後端系統整合成一個統一的入口。

系統層 — 各樓層專區

每個樓層都有自己的專區——美食街、服飾區、電器區。每個專區獨立運作，有自己的店員和收銀機。

功能層 — 每個櫃位的擺設

美食街裡每個攤位怎麼炒菜、怎麼收錢，都是具體的操作細節。

五大設計原則

  1. 各管各的（解耦）

    廚房的水管壞了，不應該影響客廳的電燈。

  2. 統一規格（介面標準化）

    家裡所有的插座都用同一種規格。

  3. 專心做好一件事（關注點分離）

    廚師負責做菜，服務生負責送餐，收銀員負責結帳。

  4. 只看菜單不進廚房（封裝）

    客人只需要看菜單點餐，不需要知道廚房裡怎麼做。

  5. 一層服務一層（分層架構）

    一樓的餐廳提供食物，二樓的健身房提供運動場地，每一層為上一層提供服務。

非功能性需求清單

功能做對了還不夠，還要考慮這些「看不見但很重要」的需求。

效能

同時會有多少人使用？可以接受多慢的回應？

Lv3+

安全性

有沒有敏感資料（密碼、個資、金流）？

Lv2+

可維護性

誰來維護？你自己？還是會交給別人？

所有層級

可用性

系統掛掉的影響有多大？需要 24 小時不停機嗎？

Lv3+

資料備份

資料丟了會怎樣？需要多久備份一次？

Lv2+

範例：寵物散步媒合平台

以下是 Vibe Requirements 探索完成後的產出範例，展示最終文件的結構與寫法。

1. 產品概述

許多上班族養了寵物卻經常加班，沒時間帶毛孩出門散步。這個平台媒合「需要遛狗服務的飼主」和「願意幫忙遛狗的散步員」，讓飼主透過 App 預約附近的散步員，並在散步過程中即時追蹤寵物狀況。

2. 複雜度評估

Lv3：服務門市（前台與後台）

這是一個典型的「內外有別」系統——就像一間便利商店：

  • 前台（飼主端）：搜尋散步員、預約服務、追蹤散步進度、評價
  • 後台（散步員端）：管理時段、接受/拒絕預約、回報散步狀態
  • 管理後台：審核散步員資格、處理糾紛、查看營運數據

3. 核心 User Stories

Must Story 1：飼主預約散步服務

作為一名飼主，
我想要搜尋並預約附近的散步員，
以便於在我無法出門時，毛孩也能得到充足的運動。

驗收標準：
1. 飼主可依地區、時段、評價篩選可用的散步員
2. 預約需填寫：日期、時段（30分鐘/60分鐘）、寵物、特殊注意事項
3. 送出預約後，散步員需在 30 分鐘內回覆接受或拒絕
4. 若超時未回覆，系統自動取消並建議其他散步員

Must Story 2：散步員管理可接單時段

作為一名散步員，
我想要設定每週可接單的時段，
以便於只在我方便的時間接到預約請求。

驗收標準：
1. 可以按週設定固定時段（例如：每週一三五 14:00-18:00）
2. 可以臨時關閉或新增某天的特定時段
3. 已有預約的時段不可被關閉（需先與飼主協調取消）
4. 時段設定後立即反映在飼主的搜尋結果中

Should Story 3：飼主即時追蹤散步進度

作為一名飼主，
我想要在散步進行中看到即時的路線與照片，
以便於安心知道毛孩的狀態。

驗收標準：
1. 散步開始後，飼主可在地圖上看到即時路線（每 30 秒更新一次）
2. 散步員可拍照上傳，飼主即時收到通知
3. 散步結束後，系統自動產生散步報告（路線圖、距離、時長、照片）
4. 飼主可對本次服務評分（1-5 星）並留言

4. 系統架構建議

  • 關注點分離：飼主端重體驗與動線引導；散步員端重效率與防呆；管理後台重數據總覽
  • 統一介面：三個端共用同一組 API，但依角色回傳不同的資料範圍
  • 封裝：地圖追蹤、通知推播、付款等功能各自獨立模組

5. Edge Cases 清單

  • 散步途中散步員手機沒電或斷網 → GPS 斷點如何處理？
  • 寵物在散步途中受傷或走失 → 緊急通知機制？保險？
  • 散步員臨時爽約 → 自動媒合替補？違約處理？
  • 飼主在散步中途取消 → 費用如何計算？
  • 惡劣天氣 → 是否自動建議改期？
  • 同一時段多隻寵物 → 散步員可以同時遛幾隻？

6. EARS 格式需求

隨時作用型：

  • 系統應該要以 HTTPS 加密所有傳輸資料
  • 系統應該要在 3 秒內回應使用者的操作

事件驅動型：

  • 當散步員點擊「開始散步」時，系統應該要啟動 GPS 追蹤並通知飼主
  • 當飼主送出預約請求時，系統應該要推送通知給散步員

異常處理型：

  • 如果 GPS 訊號中斷超過 5 分鐘，那麼系統應該要通知飼主並顯示最後已知位置
  • 如果散步員未在預約時間前 15 分鐘確認出發，那麼系統應該要發送提醒通知

狀態驅動型：

  • 當散步處於進行中狀態時，系統應該要每 30 秒更新散步員的位置到地圖上
  • 當預約處於「待確認」狀態超過 30 分鐘時，系統應該要自動取消並通知飼主

7. 非功能性需求

  • 效能：預計同時在線 100-500 位飼主，GPS 更新延遲不超過 5 秒
  • 安全性：涉及付款資訊和個資，需 HTTPS 加密、密碼雜湊儲存、付款資訊不落地
  • 可維護性：初期由 1-2 人維護，需有基本註解和模組化結構
  • 資料備份：每日自動備份，保留 30 天

8. 建議技術選型
